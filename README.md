# Лаборатори №3: Чанарын сценарио → SLO → k6 threshold

**Хичээл:** F.CSA313 — Программ хангамжийн чанарын баталгаа ба тест  
**Оюутан:** О.Мөнхзолбоо  
**Оюутны код:** B210910878  
**k6 хувилбар:** v2.2.0

## 1. Зорилго

Энэхүү лабораторийн ажлын зорилго нь жижиг API систем дээр performance, reliability, availability гэсэн чанарын шинжүүдийг сценари хэлбэрээр тодорхойлж, тэдгээрийг хэмжигдэхүйц SLO болгон хөрвүүлэх, дараа нь Grafana k6 threshold ашиглан шалгах явдал юм.

Тестийг зөвхөн өөрийн компьютер дээр ажиллаж байгаа `http://localhost:3000` локал API дээр хийсэн.

## 2. Ашигласан API

Node.js болон Express ашиглан дараах 3 endpoint бүхий локал API үүсгэсэн.

- `POST /cart/add` — хурдан endpoint
- `GET /report` — 200–400 мс санамсаргүй хүлээлттэй endpoint
- `POST /pay` — ойролцоогоор 5% магадлалтай 500 алдаа буцаах endpoint

## 3. Чанарын сценари

### 3.1 Performance scenario — `/cart/add`

1. **Тойм:** Хэрэглэгч сагсанд бараа нэмэх үед API хурдан хариу өгөх шаардлагатай.
2. **Системийн төлөв:** Express API хэвийн ажиллаж байна.
3. **Орчны төлөв:** 20 виртуал хэрэглэгч зэрэг хүсэлт илгээж байна.
4. **Гадаад өдөөлт:** Хэрэглэгч `POST /cart/add` хүсэлт илгээнэ.
5. **Шаардлагатай хариу:** Сервер хүсэлтийг амжилттай боловсруулж HTTP 200 хариу буцаана.
6. **Хэмжүүр:** `/cart/add` хүсэлтийн p95 latency 200 мс-ээс бага байна.

### 3.2 Reliability scenario — `/pay`

1. **Тойм:** Төлбөрийн endpoint-ийн алдааны хувь зөвшөөрөгдөх хэмжээнд байх шаардлагатай.
2. **Системийн төлөв:** API хэвийн ажиллаж байгаа боловч `/pay` endpoint санамсаргүйгээр 500 алдаа үүсгэж болно.
3. **Орчны төлөв:** 20 виртуал хэрэглэгч 1 минутын турш системд хүсэлт илгээнэ.
4. **Гадаад өдөөлт:** Хэрэглэгч `POST /pay` хүсэлт илгээнэ.
5. **Шаардлагатай хариу:** Төлбөрийн хүсэлтүүдийн ихэнх нь амжилттай HTTP 200 хариу авах ёстой.
6. **Хэмжүүр:** `/pay` endpoint-ийн error rate 8%-иас бага байна.

### 3.3 Availability scenario — системийн нийт хүсэлт

1. **Тойм:** Түр хугацааны серверийн тасалдлын үед системийн availability-г хэмжинэ.
2. **Системийн төлөв:** API эхэндээ хэвийн ажиллаж байна.
3. **Орчны төлөв:** 20 виртуал хэрэглэгч 2 минутын турш хүсэлт илгээж, тестийн дундуур серверийг түр зогсооно.
4. **Гадаад өдөөлт:** k6 тест ажиллаж байх үед локал API-г ойролцоогоор 8 секунд зогсоож дахин асаасан.
5. **Шаардлагатай хариу:** Сервер дахин асмагц хүсэлтүүдийг хэвийн боловсруулж эхэлнэ.
6. **Хэмжүүр:** Нийт check-ийн амжилтын хувь 90%-иас их байна.

## 4. SLO ба k6 threshold

| Чанарын шинж | SLI | SLO | k6 threshold |
|---|---|---|---|
| Performance | `/cart/add` p95 latency | p95 < 200 ms | `http_req_duration{name:cart}: p(95)<200` |
| Performance (`/report`) | `/report` p95 latency | p95 < 450 ms | `http_req_duration{name:report}: p(95)<450` |
| Reliability | `/pay` error rate | error rate < 8% | `http_req_failed{name:pay}: rate<0.08` |
| Availability | Амжилттай check-ийн хувь | > 90% | `checks: rate>0.90` |

`/cart/add` нь хурдан endpoint учраас 200 мс-ийн p95 босго сонгосон. `/report` нь зориудаар 200–400 мс хүлээлттэй учраас 450 мс-ийн p95 босго сонгосон. `/pay` endpoint ойролцоогоор 5% санамсаргүй алдаа үүсгэдэг тул 8%-иас бага error rate-ийг SLO болгосон. Availability-ийн хувьд нийт check-ийн 90%-иас дээш нь амжилттай байх шаардлага тавьсан.

## 5. Хэвийн тестийн үр дүн

`results/pass.txt` файлд 20 VU, 1 минутын хэвийн тестийн үр дүн хадгалагдсан.

| Үзүүлэлт | Үр дүн | SLO | Төлөв |
|---|---:|---:|---|
| `/cart/add` p95 | 0 s | < 200 ms | PASS |
| `/report` p95 | 397.88 ms | < 450 ms | PASS |
| `/pay` error rate | 5.07% | < 8% | PASS |
| Checks | 98.30% | > 90% | PASS |

Нийт 927 iteration, 2781 HTTP request хийгдсэн. Нийт 2781 check-ээс 2734 нь амжилттай, 47 нь амжилтгүй байсан. Хэвийн ажиллагааны үед бүх үндсэн threshold шаардлагыг хангасан.

## 6. Зориудын FAIL тест

Threshold ажиллаж байгааг батлахын тулд `slo-test-fail.js` файлд `/report` endpoint-ийн threshold-ийг:

```text
p(95)<100
```

болгон зориудаар хэт хатуу тохируулсан.

Тестийн үр дүнд:

- `/report` p95 = **397.65 ms**
- шаардлага = **p95 < 100 ms**
- үр дүн = **FAIL**
- checks = **98.02%**
- `/pay` error rate = **5.92%**
- нийт check = **2784**
- failed check = **55**

`397.65 ms > 100 ms` учраас k6 threshold crossed гэсэн алдаа гаргаж тест FAIL болсон. Энэ нь threshold зөрчигдөх үед k6 тестийг амжилтгүй гэж зөв илрүүлж байгааг харуулсан.

## 7. Chaos / Availability тест

Chaos тестийг 20 VU, 2 минутын хугацаатай ажиллуулсан. Тестийн явцад локал Express серверийг ойролцоогоор 8 секунд зогсоож, дараа нь дахин асаасан.

`results/chaos.txt` үр дүн:

- Нийт хүсэлт/check: **5646**
- Амжилттай: **5123**
- Амжилтгүй: **523**
- Амжилтын хувь: **90.73%**
- `/cart` — 1735 амжилттай, 147 амжилтгүй
- `/report` — 1733 амжилттай, 149 амжилтгүй
- `/pay` — 1655 амжилттай, 227 амжилтгүй
- `/pay` error rate = **12.06%**
- `/report` p95 = **398.14 ms**
- `/cart` p95 = **447.97 µs**

Availability:

```text
Availability = successful / total × 100
             = 5123 / 5646 × 100
             = 90.73%
```

Иймээс `checks > 90%` availability SLO нь **PASS** болсон.

Гэхдээ `/pay` error rate 12.06% болсон тул `rate < 8%` reliability threshold **FAIL** болсон. Серверийг бүхэлд нь зогсоосон үед зөвхөн availability биш `/pay` хүсэлтүүд мөн connection failure болсон учраас reliability SLI-д нөлөөлсөн.

## 8. Error budget

Availability SLO = 90% тул зөвшөөрөгдөх failure budget нь 10%.

2 минут = 120 секунд учраас time-based error budget:

```text
120 × 0.10 = 12 секунд
```

Иймээс time-based байдлаар 12 секунд хүртэл unavailable байх budget гарч байна. Туршилтын үед сервер ойролцоогоор 8 секунд зогссон тул энэ хугацаа 12 секундийн time-based budget дотор байсан.

Request-based error budget:

```text
5646 × 0.10 = 564.6
```

Өөрөөр хэлбэл ойролцоогоор 564 хүсэлт алдагдах боломжтой. Бодит тестээр 523 хүсэлт/check амжилтгүй болсон бөгөөд энэ нь request-based budget-аас бага байна.

Time-based болон request-based error budget нь ижил утгатай биш. Time-based budget нь систем хэдэн секунд unavailable байж болохыг хэмждэг бол request-based budget нь нийт хүсэлтээс хэд нь амжилтгүй байж болохыг хэмждэг. Тасалдлын үед олон VU зэрэг хүсэлт явуулж байгаа учраас богино хугацааны outage ч олон failed request үүсгэж болно.

## 11. Дүгнэлт

Энэ лабораторийн ажлаар чанарын шаардлагыг шууд ерөнхий байдлаар бичихээс илүү хэмжиж болох SLO болгон тодорхойлох нь чухал гэдгийг ойлгосон. Performance тестээр `/cart/add` болон `/report` endpoint-ийн p95 хугацааг тусад нь хэмжиж threshold ашиглан шалгасан. Хэвийн тестийн үед `/report` p95 397.88 мс байсан бөгөөд 450 мс-ийн шаардлагыг хангасан. `/pay` endpoint-ийн error rate 5.07% гарсан тул 8%-ийн SLO-г мөн хангасан. Дараа нь `/report` threshold-ийг зориудаар 100 мс болгож өөрчлөхөд тест FAIL болсон нь k6 threshold зөв ажиллаж байгааг харуулсан. Chaos тестийн үед серверийг түр зогсооход нийт амжилтын хувь 90.73% болж буурсан. Мөн серверийн тасалдал `/pay` endpoint-д нөлөөлж error rate-ийг 12.06% болгосноор reliability threshold FAIL болсон. Error budget-ийг хугацаагаар болон хүсэлтийн тоогоор тооцоход хоёр хэмжүүр өөр утга илэрхийлдэг болохыг туршилтаар харж чадсан. Ерөнхийдөө энэ лабораториор quality scenario, SLO, SLI болон k6 threshold хоорондоо хэрхэн холбогддогийг практик дээр ойлгосон.
